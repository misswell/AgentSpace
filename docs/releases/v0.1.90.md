# 0.1.90 — Agent 窗口在用的时候不再先掉到 5 帧

**直接更新 App 即可，这次修复在 App 里。** Worker、CLI、特权助手和 wire 协议都没有行为变化，
不需要重新登录；正在运行的 Worker 会像往常一样被 App 换成同版本（需要时会有一次 macOS 管理员
授权）。如果更新后界面因为版本号提示特权助手需要更新，按一次「重新安装助手…」只是把版本对齐，
和本次的流畅度修复无关，可以稍后再做。

**为什么一个窗口卡、整个桌面不卡。** 采集窗口的那条流是独立的 window stream，macOS 只在
这个 App 自己重绘时给帧；画面安静 1.5 秒后，旧策略把采集上限降到 5 帧/秒的省电探测档，下一批
内容到来时又要先发一次配置更新，所以每一段新画面都从 5 帧起步。桌面的 display stream 一直
有内容在变，很少进入这个档位。2026-10-20 的日志里量到：同一个 worker 上，桌面关闭时约
**20.9 帧/秒**，被使用的窗口 **21.6 帧/秒**，而安静的窗口只有 **4.4 帧/秒**——客户端把收到的
每一帧都渲染了（`dropped=0 gaps=0`），主线程和布局开销都是 **0.0/秒**，卡在源头没有新帧。

**现在采集上限跟着“注意力”走，而不是跟着一帧一帧的内容走。** 只要窗口是当前窗口，或者指针
在它的画面上，采集就保持你设置的上限——画面静止时这不产生任何帧，因此几乎不占资源；下一段
内容可以在满速下被采到，不再从探测档爬升。速率也不会再因为一次内容突发放大、1.5 秒静默后
又掉回去，反复重配同一条流。桌面视图使用同一条规则，所以两边的手感来自同一套决定。

**没有把窗口改成整屏采集。** 那样既不会让 App 多画一帧，还会把盖在窗口上的其他窗口一起拍
进来、把一个窗口的画面连带整屏内容送过 socket。能统一的传输、解码、渲染和限速本来就已是同
一套代码；这次统一的是速率决策。

**省电的部分保留。** Agent 窗口每 0.25 秒核对一次注意力：指针离开且窗口失去焦点、画面也安静
1.5 秒后，回到 5 帧/秒的探测档。桌面视图在下一次有帧或手势时核对；画面本身不动时没有帧可采，
高上限不产生开销。最小化时采集直接停止。

验证证据见 validation §391（注意力保持上限、离开后仍给 1.5 秒宽限、按住按钮仍优先于注意力、
以及层 1–3 的实跑数字）。层 4 不会打开 Agent 窗口去拖动它，因此真实窗口的帧率曲线仍只有策略
单测与日志上的旧测量作证，这一点照实记在该节。
