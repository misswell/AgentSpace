# 0.1.85 — 账号休眠时，登录入口排在卡片第一行；两处入口各有了自己的名字

更新 AgentSpace 到 0.1.85。**需要你做的两件事**：

1. 如果账号页显示「休眠 / Worker 未运行」或桌面被锁，现在「权限与授权」卡片的**第一行**就是强调按钮「登录 / 解锁 Agent」——不用再往下翻。其余流程与 0.1.84 相同：点它，在 macOS 的登录窗口里认证，让那个窗口保持可见，三项授权在这一次进入里勾完。
2. 如果你用辅助功能、快捷指令或任何脚本**按标识名**来找这两个按钮，名字换了，而且现在两个界面各有各的名字：

| 界面 | 旧标识名 | 新标识名 |
|---|---|---|
| 账号详情页「权限与授权」卡片 | `signInAgent` | `agentSignInDoorCard` |
| 桌面查看器的锁定遮罩 | `signInAgent` | `agentViewerSignInDoor` |
| 新建 Agent 向导：名称输入框 | `agentNameField` | `newAgentNameField` |
| 新建 Agent 向导：macOS 账户选择 | `macOSUserPicker` | `newAgentUserPicker` |
| 新建 Agent 向导：继续按钮 | `wizardContinue` | `newAgentContinue` |
| 构建号文本 | `appBuildVersion` | `appBuildVersionStamp` |

**为什么改位置。** 0.1.84 的截图说明了这件事：账号 `misswell` 休眠、Worker 未运行、会话未知，卡片上看得见的是「打开辅助功能设置」「打开屏幕录制设置」「打开完全磁盘访问权限设置」，而唯一能进入那个会话的入口排在它们后面。上一轮为了「一页只有一个登录入口」把它搬进这张卡片，位置却搬错了——在最需要它的状态里，它成了最后一个。现在入口按状态决定位置：Worker 离线或桌面锁定时排在卡片最前，账号健康时留在授权按钮之后，两种情况下页面上仍然只有一个（两个分支互斥），说明文字里的「上方／下方」跟着位置一起变。

**为什么换名字，以及一条我们写错又改回来的结论。** 这一版给发布流程加了一道检查：在签名之前，先读**即将打包出去的那份二进制**，把验证脚本要按的标识名逐条核对。为此我们最初把「发布字节里搜不到 `signInAgent`」读成了「发布出去的按钮没有名字」——这个结论是错的，已经撤回。把整份文件按 ASCII、UTF-16LE、UTF-16BE 扫过，`signInAgent` 确实是 0 次；但把标识名逐条拿去和**生成它的那份源码**比对之后规律很干净：0.1.84 自己那 62 个标识名对着它自己发出去的 7,484,320 字节二进制，**缺的 8 个全部 ≤15 字节**（`signInAgent` 11、`fusionAppRow` 12、`fusionAppList` 13、`agentNameField` 14、`wizardContinue` 14、`macOSUserPicker` 15、`appBuildVersion` 15、`updateStateText` 15），**在的 54 个最短是 17 字节**，一个例外都没有；这一版的 63 个名字对着这一版的 release 构建，只有 3 个缺——就是我们有意保留没改的那三个短名字——而 16 字节的 `newAgentContinue` 已经在字节里了，15／16 的分界因此两边都有实测样本。同一批旧名字在 §385 的 debug 构建里一个不缺。原因是 Swift 把 ≤15 字节的 ASCII 字面量直接装进 `String` 自己的两个字里，优化构建用 `mov`/`movk` 半字立即数生成它，永远不会在 `__cstring` 里留下连续字节——反汇编里能看到 `mov x0, #0x6e49`（"In"）这类片段。也就是说：**运行时那个按钮一直有名字，只是短名字在字节层面查不到。** 这里还有一次自己的更正：第一版统计写的是「54 个里缺 4 个」，那是拿**这一版**的名字去扫**上一版**的二进制，六个新改的名字因此被算成「缺」——缺的原因和长度无关——而四个真正短的旧名字根本没进列表。行 1249 记的是重测过的三对数据。于是这道检查只对足够长的名字有意义，上面这六个标识名因此改到 16 字节以上，两个入口也顺势拆成各用自己的名字——它们可能同时在屏，一个共用名字说不清搜到的是哪一个。向导之外没被脚本按过的短名字（例如 `fusionAppRow`）我们没动。

**这一版仍然没有改变的部分。** macOS 一个隐私类别只弹一个面板，三项授权依旧是三次开关，改变的只是它们发生在一次进入、不切换用户的同一个会话里；控制台账号永远看不到这个入口（那个会话就是你自己的屏幕，§3 禁止任何驱动它的路径）；关闭向导只结束这次临时查看，§376 的屏保与延时解锁组合仍让那个桌面在窗口消失后不自动锁屏；密码始终由人在 macOS 里输入，AgentSpace 不代填、不记录、不写 TCC 数据库。多显示器时 Apple 的屏幕共享窗口显示一块还是两块，是那个客户端自己的选择（开关在它的面板里），我们不去脚本化别人的界面。

验证证据见 validation §386（行 1248–1259：0.1.84 发布字节的复核、三对「源码↔由它构建的二进制」的长度分界测量、撤回与更正、release 前置门禁与其四条防腐测试、层 1–3 的实跑结果与 21/21 的打包字节复核、这道门禁自己在构建机上误杀一次正确构建的经过、本地构建因为没有 Developer ID 而签出 ad-hoc 却被脚本判为 ok 的陷阱、发布读回的通道/构建机/Apple 三方记录，以及对**下载回来的那份二进制**再跑一次 21 个标识名全在，以及层 4 这一版**没有**任何可用工具可执行的事实与原因）。GitHub 发布页面上那一份写的是「行 1248–1256」——页面文字取自标签所在的提交，而 1257–1259 三行是在标签之后、发布读回之后补进去的。

**这一版的发布过程里，出问题的是检查本身。** 这道字节门禁第一次在 GitHub Actions 上真跑时，把一份**没有任何问题**的构建挡了下来：21 个标识名报出 18 个「缺失」。原因不在 Swift，而在脚本——它把一兆字节的 `strings` 输出用管道交给 `grep -q`，`grep` 一命中就退出，`printf` 因此收到 SIGPIPE，而 `set -euo pipefail` 把这当成检查失败。日志里每一条「缺失」前面都跟着一行 broken pipe，恰恰证明那 21 个名字全都在二进制里。改成先写临时文件再逐条比对后，`./scripts/release.sh` 端到端 21 个全过。那一次运行没有发布任何东西，也没有向 Apple 提交任何文件，所以没有用户拿到过有问题的字节；版本号仍是 0.1.85，标签在真正发布成功之前重切过两次，GitHub 上直到第三次运行成功才第一次出现 0.1.85 这个页面。
