# 0.1.80 — 桌面观看者不再崩溃（窄窗口的对齐死循环）

更新 AgentSpace 到 0.1.80 就行：**这一次只改 App 本身**，在应用里点「检查更新」装完即生效，不动 Worker、不动特权助手，也不需要管理员授权。**如果你的桌面观看者之前崩过，什么都不用清理**：装好后直接打开就行——越界的窗口尺寸记录会被自动拉回屏幕内，窄窗口会被自动加宽到比例能成立的最小宽度。

**崩溃是什么**

今天下午五份崩溃报告（16:13、16:29、17:02:25、17:02:58、17:03:53）是同一个机制，只是终止方式不同：有的走 `NSApplication` 捕获异常后自杀（SIGTRAP），有的让异常从显示周期里逃出去（SIGABRT）。系统日志里 AppKit 自己把原因写得很直白——那扇窗口在一个显示周期里被要求「再算一次约束」的次数超过了它自己的上限：

```
Marking window … as needing Update Constraints in Window … (limit: 47, count: 49 w/identifier …)
```

两方在同一个显示周期里来回改同一扇窗的尺寸：一方是 `DesktopViewerWindowController.viewportDidLayout`（把画面区对齐到远端桌面的宽高比，好让桌面不变形），另一方是 SwiftUI 的 `NSHostingView.updateAnimatedWindowSize`（把窗口保持在内容自己的最小尺寸之上）。两边都「对」，尺寸互相推翻，直到 AppKit 的预算被顶穿。

**为什么只在窄窗口上炸，以及为什么是 0.1.79 才炸**

算术上这两边的要求在一个窄窗口里无法同时成立：749 pt 宽的窗口按 16:9 只该有 421 pt 高的画面区，但观看者的内容最小值是 520 pt。SwiftUI 守住 520（把窗口拉回 552），对齐守住比例（把窗口压到 454），两个数都不动。

是不是 0.1.79 引入的，是量出来的，不是推出来的——同一份「已保存的窗口尺寸」分别喂给三个构建（都在 `/tmp` 里编译，源码来自 git tag 与工作区，全程没有碰 `dist/`）：

| 构建 | 结果 |
|---|---|
| 0.1.78 源码 | 活着，窗口停在 749×552（SwiftUI 的最小值说话，画面略被拉伸） |
| 0.1.79 源码（＝发布出去的字节） | **崩溃** |
| 0.1.79 源码去掉 `.ignoresSafeArea(.container, edges: .top)` | 活着，窗口 749×552 |
| 0.1.79 源码去掉 `.frame(minHeight: titlebarHeight)` | **仍然崩溃** |

也就是说，致命的那一行是 §380 释放顶部安全区这件事本身，而不是那行「控件条高度跟着标题栏走」——去掉后者的 0.1.79 一样崩。释放安全区之后，内容铺满整窗，而 `NSHostingView` 算窗口尺寸时仍会把标题栏留在内容最小值之上，于是「SwiftUI 想要的窗口」和「对齐想要的窗口」在任何尺寸下都差着一个标题栏，窄窗口上就变成永远打不平的来回。

**改了什么**

1. **对齐不再在量出尺寸的那次布局过程里改窗口**：`viewportDidLayout` 只记录画面区尺寸，实际的对齐延后一拍（`DispatchQueue.main.async`）执行，执行前重新核对比例是否仍然不对。AppKit 的警告 `It's not legal to call -layoutSubtreeIfNeeded on a view which is already being laid out` 在修后的运行里不再出现。
2. **对齐目标必须同时满足比例和观看者自己的最小值**：`DesktopViewportSizing.contentSize` 改为在「比例允许的宽度区间」里取值——下界来自最小视口（宽 720、高 520）和比例，上界来自屏幕的可用区域；窄窗口因此**加宽**（749 → 约 924），而不是把画面区压到最小以下。区间为空时（例如竖屏比例的远端桌面在矮屏上）返回 `nil`，调用方记一行 `no re-fit is available` 后什么都不做，而不是继续拉扯。
3. **越界的保存尺寸拉回屏幕内**：窗口上屏后如果 frame 有一角在可见区域之外（这种窗口的标题条抓不到，等于死窗），`DesktopViewportSizing.onScreenFrame` 把它移回可见区域，尺寸超出屏幕时才缩小。

**实测（都在子账号自己的会话里，临时构建 + `AGENTSPACE_ROOT` 指向一份临时注册表，深链接开窗口）**

- 崩过的那个窗口（`610 -520 749 552`，就是你机器上 `defaults read` 出来的原值）：现在只做一次对齐，然后安静下来——
  `conform #1 viewport 749x520, expected height 421: window 749x552 → asked 924x552 → 925x552`，
  紧接着 §380 那行 `control strip occupies 520..552 of a 552 pt window; title bar is 32 pt, so the strip starts 0 pt below the top edge — one row with the window buttons`。90 秒里 `conform` 只出现一次（旧构建在同一时段里是几十次/秒的来回）。
- 比例正确的 1120×662 窗口：一次对齐都不需要。比例不对但够宽的 1120×900：一次对齐到 1120×662。
- 拖角改尺寸仍然锁比例：1120×662 拖到 1025×609，画面区 1025/1.7778 = 576.6 对实测 577——顺手拖窄会被停在比例能成立的最小宽度上。
- 控件条上的 ⓘ（坐标 1472,156）照常弹出并锚在按钮下方；拖控件条中间空白（1000,155 → 1080,215）窗口位移正好 +80/+60，尺寸不变。

**这一版没有解决什么**

- **窄窗口的代价**：16:9 的远端桌面下，观看者窗口不能再被拖到约 924 pt 宽以下——这是「不变形」优先于「更窄」的选择。竖屏这类比例在屏幕装不下最小值时，画面会按拉伸显示，日志会写一行 `no re-fit is available`；这是本轮接受的上限，不是遗漏。
- 验证是**手开窗口**做完的（`agentspace exec` + 深链接 + 截图/AX 读数）；`scripts/gui-verify.sh`（会关掉你名下所有 AgentSpace 实例、把窗口开在你屏幕上）这一版没有跑。第 4 层门禁跑的是会话里的替身。

**安全边界**

本版没有新增任何密码入口、密码日志字段、注册表字段、特权助手操作或 agent RPC；`HelperProtocol` 的操作清单、协议方法名和 `protocolVersion` 都没有动。改的是 App 的窗口算术与改尺寸的时机，新增的是 App 自己的两行诊断日志（category `viewer-conform`）。
