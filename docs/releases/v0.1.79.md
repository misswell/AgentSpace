# 0.1.79 — 桌面观看者的顶栏和三个窗口按钮合成一行

更新 AgentSpace 到 0.1.79 就行：**这一次只改 App 本身**，在应用里点「检查更新」装完即生效，不动 Worker、不动特权助手，也不需要管理员授权。然后打开某个账号的桌面观看者，顶栏应该是一行：红绿灯（关闭／最小化／缩放）和右边那一排控件（重连、暂停、画质、帧率、鼠标捕获、截图、ⓘ、✕）在同一条带上。

**为什么上一版没做到**

0.1.63 那次（§361）就写了「控制条就是标题栏」，代码也确实给窗口加了 `.fullSizeContentView`、把标题栏设成透明、标题不画——但窗口里从来不是这样。原因是 AppKit 的一条行为，源码里看不见：SwiftUI 内容装进 `NSHostingView` 时，标题栏的高度会作为**顶部安全区**交给 SwiftUI，于是整条控件条被往下推了一个标题栏的距离，红绿灯独占一行，控件条成了第二行。那一版的记录里其实写了「合并后的样子待肉眼确认」，这次你的截图把这句话结清了：没合并。

这一版就是释放那个顶部安全区（`ignoresSafeArea(.container, edges: .top)`），一行代码的事，但先测了三件事再动手——都在子账号自己的会话里测，没有占用你的屏幕：

- **控件画进标题栏那条带里，还收得到点击吗？** 收得到。用一个和观看者窗口同样式的一次性探针窗口，控件条顶边落在窗口顶边（SwiftUI 报 `(0, 0, 700, 28)`，标题栏实测 32 pt），`agentspace click` 打在那条带里的按钮上，按钮自己的动作日志回来了。
- **那条带的空白处还能拖动窗口吗？** 能。拖控件条右半的空白（1010,192 → 1110,292），两张截图里控件条的顶边从 178 走到 278、左边从 610 走到 710，正好是拖动的位移。
- **那个「标准做法」行不行？** 不行，而且会撞车。`NSTitlebarAccessoryViewController` 配 `.leading` 是往标题栏放视图的正规 API，但它的宿主视图落在 `(18, 5, 120, 22)`——压在红绿灯上面，截图里缩放按钮的位置被它盖住了。它是给工具栏项目用的，不是一条通宽的控件条。

**顺手补了「说了没做」的那类错，并把这条错测出来了**

§361 的错不在于没做，在于用代码和构建通过当作界面已经成立。所以这一版让窗口自己说：桌面观看者每次开窗口会往日志里写一行（subsystem `com.agentspace.app`，category `viewer-chrome`），内容大致是

```
control strip occupies 728..760 of a 760 pt window; title bar is 32 pt, so the strip starts 0 pt below the top edge — one row with the window buttons
```

结尾是 `one row with the window buttons` 就是一行；如果写成 `a second row below them`，说明这次没合上，那行日志里的数字就是问题所在。这个数字是控件条自己的视图报出来的，不是从「窗口高减去画面高」推出来的——后者在两种情况下算出来都是「控件条高度」，等于什么都没测。

这行日志不是白写的：**它在真窗口上第一次读回来，就发现合并是对的、对齐是错的**。那一行是 `736..760`，也就是控件条只有 24 pt，而标题栏是 32 pt——顶边贴着窗口顶边（所以确实是一行），但红绿灯是 AppKit 在 32 pt 里垂直居中的，于是控件条里的文字中心落在 `y=100`，灯的中心在 `y=104`，差 4 pt。一行不同心，看着还是两行。修法是控件条的高度跟着标题栏那条带走（`window.frame.height − contentLayoutRect.height`），修后同一窗口的中心是 **103.5 对 104.0**，日志也变成上面的 `728..760`。这个 4 pt 只在真实窗口上量得出来，所以这一版宁可把发布流程在中途停掉（run 38031557398 在签名阶段取消，`releases/latest` 当时仍是 v0.1.78，标签重打在修好对齐的那个 commit 上），也不发一个「合了但没对齐」的版本。

**同一扇真窗口上还测了这两条**

- **ⓘ 详情气泡**：点在标题栏带里的 ⓘ（`click 1485 105`）气泡照常弹出并锚在按钮下方，显示「● ChromeShot 休眠 / uid 503 / 空闲休眠 / ☐ 性能信息浮层」——合并没有弄坏它。
- **拖动**：拖控件条中间空白（`drag 900 105 → 980 165`），窗口位移正好是 +80/+60（左边 401→481，顶边 89→149），点击穿透没有发生。

以上都在这台 Mac 之外的那个子账号会话里量（临时构建装在 `/tmp`，用 `AGENTSPACE_ROOT` 指一份空注册表，深链接开桌面观看者），你正在用的那个 App 实例（pid 23552）全程没有被关掉或替代，测完的临时 bundle、截图和它留在该账号偏好里的窗口尺寸记录都已删掉。

**这一版没有解决什么**

最右边那两个图标（ⓘ 与 ✕）的视觉中心没有被干净地量出来：它们贴着窗口的圆角和投影，像素扫描在那里给出的行号前后不一致，所以这两个字形是靠同一条带的高度和控件条自己的上下留白摆正的，不是量出来的。

第 4 层门禁这一版跑的是**会话里的那一半**：`scripts/session-gui-verify.sh` 在子账号自己的桌面里对临时构建的 0.1.79 bundle 答 **14/14 通过**，同一时刻未改动的 `dist/AgentSpace.app`（0.1.78）也是 14/14，所以这不是「候选自己和自己比」。（第一次跑曾报 `launch opens exactly one window: expected [1] got [2]`——那是我自己上一轮量对齐时留下的观看者窗口还开着，同一个 bundle identifier 共用一份窗口恢复状态；关掉后重跑就是一条窗口、14/14。）但这两次跑的都是**管理窗口**，两个替身都不会开桌面观看者，`gui-verify.sh`（会关掉本机你这个用户的所有 AgentSpace 实例、并把窗口开在你屏幕上）这一版完全没跑。上面那一串顶栏数字来自临时 bundle＋空注册表＋深链接手量的观看者窗口（§380 rows 1187–1189、1191），不是门禁产物。

**安全边界**

本版没有新增任何密码入口、密码日志字段、注册表字段、特权助手操作或 agent RPC；`HelperProtocol` 的操作清单、协议方法名和 `protocolVersion` 都没有动。改的只有 App 的窗口布局，加的是 App 自己的一行诊断日志。
